# 합성 사용자 평가 지침 v1

## 목적과 표시

현재 안국·서촌 장소 비교 앱을 사용한다고 가정한 100개 사례로 개선 가설을 만든다. 모든 사례는 **AI가 작성한 가상 사용자 조건 및 예상 반응**이다. 실제 방문객, 실제 인터뷰, 100개의 독립적인 브라우저 세션이 아니다. 실제 조사 파일(recruitment.csv, sessions.csv, observations.csv)에 합성 내용을 섞지 않는다.

## 구성

- 비교쌍 4개 × 사용 조건 25개 = 100개 사례. 각 지역 50개, 각 비교쌍 25개.
- 실제 유동인구 구성비를 모르는 상태이므로 인구통계 비율, 국적·직업·나이 분포를 만들어 대표 표본이라고 부르지 않는다.
- 비·햇빛·짧은 체류·예산·유모차·보행 부담·언어·네트워크 등의 사용 조건은 가정이다. 현재 날씨나 현장 상태에 대한 주장으로 사용하지 않는다.
- 조건 순서만 고정 seed 20260929로 섞는다. 이는 실제 사람을 무작위로 뽑는 절차가 아니다.
- 한 명의 분석자가 대표 UI 흐름을 확인하고 동일한 근거를 각 조건에 적용한다. 독립된 AI 100명이 의견을 냈다고 주장하지 않는다.

## 재사용 프롬프트

```text
너는 장소 비교 앱의 합성 사용자 평가자다.
입력: 현재 앱 버전, 확인된 화면/동작 근거, 비교쌍, 사용 조건.

1. 외모·성별·나이로 행동을 단정하지 말고 주어진 목적과 제약만 적용한다.
2. 해당 사용자가 비교 → 상세 → 지도 → 외부 지도 → 복귀에서 필요로 할 정보를 적는다.
3. 앱에 실제로 있는 기능과 없는 정보를 구분한다. 없는 버튼이나 사용자 경험을 지어내지 않는다.
4. 코드 근거, 직접 확인한 UI 동작, 예상 반응을 각각 표시한다.
5. 가상 피드백은 반드시 '합성 발언'으로 표시한다. 실제 인용으로 쓰지 않는다.
6. 결과는 '판단 근거 있음 / 추가 확인 필요 / UI 마찰 가능 / 실행 미확인'으로 표현한다.
   사용자 성공률, 만족도 평균, 이탈률, 실제 도보 시간은 생성하지 않는다.
7. 긍정적인 측면, 막히는 지점, 최소 개선안, 실제 사람에게 확인할 질문을 기록한다.
8. 비용·입구·운영 여부·접근성을 모르면 모른다고 한다. 현장 방문 완료를 주장하지 않는다.
9. 문제 빈도를 합성 인원으로 증명하지 않는다. 조건 배분이 빈도를 결정하기 때문이다.
10. 개선은 기존 기능의 가림·문구·배치를 먼저 다룬다. 새 기능은 사용 목적에 꼭 필요할 때만 제안한다.
```

## 근거 등급

- UI: 이번에 실제 브라우저에서 화면/전환을 확인한 사실.
- CODE: index.html, js/app.js, js/map.js, js/data.js, css/app.css에서 확인한 사실.
- HYP: 해당 조건에서 사용자가 어려움을 느낄 수 있다는 추론. 실제 사람의 반응 미확인.
- UNTESTED: 실제 야외 눈부심, 이동 접근성, 스크린리더, 느린 네트워크, 외부 지도 앱 복귀, 실제 입구 도착 등 실행하지 않은 조건.

## 실행 및 결과 읽기

`python research/build_synthetic_cases.py`는 편집된 25개 조건과 4쌍의 근거를 결합해 synthetic_cases.csv를 만든다. 브라우저 자동 사용 프로그램이나 인간 행동 예측 모델은 아니다. 생성된 피드백은 규칙 기반의 가설이며 실행 결과를 흉내 내는 수치를 넣지 않는다.

우선순위는 행동을 막는 정도, 자료 확실성, 수정 범위를 보고 정한다. 실제 검증에서는 가설에 동의하는지만 묻지 말고, 해당 행동을 관찰한다. 결과 보고서는 SYNTHETIC_REVIEW.md에 있다.
